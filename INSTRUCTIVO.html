DataPipeline — Instructivo del proyecto

Guía práctica de qué es el sistema, cómo está organizado, qué hace cada pieza (incluido el CLI), cómo se ejecuta y cómo se prueba. Estado al 2026-06-22.

.NET 10 Fases 1–3 + 4A completas 58 tests verdes Build pristine

1 Qué es DataPipeline

Es un middleware de integración de datos propio (solución .NET 10 separada e independiente de ConsultasGenericas). Su trabajo:

Leer de un origen (hoy SQL Server) → transformar los datos (renombrar / castear / calcular / filtrar columnas) → dejarlos en una tabla de serving intermedia → exponerlos por una API PULL autenticada para que otros sistemas los consuman.

Es PULL: el middleware no empuja a destino; deja los datos servidos y el consumidor los retira por HTTP (GET) y confirma lo que tomó (ack). El destino final lo decide el consumidor.

Todo corre por streaming y por lotes (no materializa todo en memoria) y los pipelines se definen de forma declarativa (sin escribir código): origen + transformaciones + tabla destino + horario.

2 Arquitectura: los proyectos y para qué sirve cada uno

La solución (DataPipeline.slnx) tiene 7 proyectos de producción + 3 de tests:

DataPipeline.Core         ← contratos y modelos puros (sin dependencias externas)
DataPipeline.Connectors   ← implementaciones concretas (SQL Server, SQLite, transforms, cifrado)
DataPipeline.Engine       ← el motor: arma y corre la tubería; scheduler; hidratación
DataPipeline.Persistence  ← almacén A (EF Core/SQLite): definiciones + historial + datasources
DataPipeline.Api          ← host web: endpoints HTTP, auth, scheduler de fondo (deployable)
DataPipeline.Admin        ← UI de administración (Blazor Server + Syncfusion)
DataPipeline.Cli          ← utilitario de línea de comandos (ver sección 4)
tests/*                   ← DataPipeline.Tests, .Persistence.Tests, .Api.Tests (58 tests verdes)

Cómo se relacionan: Core define las interfaces; Connectors y Persistence las implementan; Engine orquesta usando esas interfaces. Después hay tres "caras" del mismo motor: Api (HTTP), Admin (visual) y Cli (línea de comandos).

Detalle por proyecto

ProyectoResponsabilidad
CoreModelos de dominio (PipelineDefinition, StepDefinition, PipelineRun, DataSource, enums) y contratos (ISource, ITransform, IDataStore, factories, stores, cifrado…). No referencia nada externo.
ConnectorsSqlServerSource (lee de SQL Server en streaming), SqliteDataStore (serving con ciclo de procesado), ColumnMapTransform (transform con NCalc), factories, EncryptionService (AES), ConnectionTester.
EnginePipelineRunner (compone Source→Transform(s)→DataStore por lotes), PipelineHydrator (resuelve dataSourceId→conexión), ScheduleCalculator, EjecutorProgramado (corre los vencidos).
PersistenceMetadataDbContext (EF Core/SQLite, "almacén A") + repos + migraciones. Guarda definiciones, historial y datasources (secretos cifrados).

AdminBlazor Server + Syncfusion. UI para gestionar datasources y pipelines, dispararlos y ver el historial, sin escribir JSON. Habla con la Api por HTTP.
CliUtilitario de consola — ver sección 4.

3 El flujo de datos (end-to-end)

[SQL Server origen]
      │  (SqlServerSource, streaming por lotes)
      ▼
[Transform(s): rename / cast / computed / filter]   (ColumnMapTransform, NCalc)
      │
      ▼
[Serving SQLite]  ← cada fila lleva columnas de control: _key, _creado, _procesado
      │
      ▼
GET /api/data/{pipeline}   ← el consumidor retira SOLO lo no procesado
      │
      ▼
POST /api/data/{pipeline}/procesar  ← el consumidor confirma (ack) las keys que tomó

Ciclo de procesado (Fase 4A): cada fila del serving tiene _key (identidad, de las "columnas clave" del pipeline), _creado (cuándo se escribió/actualizó) y _procesado (0 hasta que el consumidor la confirma).

Modo de escrituraComportamiento
AgregarCada corrida inserta lo nuevo; al inicio de la siguiente borra las ya procesadas (para no acumular).
ReemplazarUpsert por _key: si la key existe la actualiza (_creado=now, _procesado→0); si es nueva la inserta; las ausentes quedan.

Programación: un pipeline puede ser BajoDemanda (a mano) o Diaria/Semanal/Mensual (el scheduler de la Api lo corre solo a la hora configurada).

4 El proyecto CLI — qué es y para qué sirve

DataPipeline.Cli es una aplicación de consola que maneja el mismo motor que la Api (referencia Core/Connectors/Engine/Persistence), pero desde la línea de comandos, sin levantar la Api ni el Admin. Es una herramienta de desarrollo / operaciones / automatización.

La Api es el motor "como servicio" (HTTP + scheduler + UI detrás). El CLI es el motor "como herramienta" (un comando, una corrida). Misma maquinaria, distinta cara.

Por qué existe: nació como el entregable de Fase 1 — probar que el motor funciona end-to-end antes de que existieran la Api, el scheduler o la UI. Sigue siendo útil para automatizar (scripts, tareas programadas, CI), bootstrap (cargar pipelines sin la UI), pruebas rápidas y diagnóstico.

Sus 3 modos (subcomandos)

1. Correr un pipeline ad-hoc desde un JSON (modo por defecto):

dotnet run --project DataPipeline.Cli -- <pipeline.json> <salida.sqlite> [claveBase64]

Carga un pipeline definido en un archivo JSON y lo corre una vez, escribiendo a una SQLite. No usa la BD de metadatos ni el scheduler: la forma más directa de probar un pipeline.

2. Importar una definición al almacén A:

dotnet run --project DataPipeline.Cli -- import <pipeline.json> <metadata.db>

Registra (upsert) un pipeline desde JSON en la BD de metadatos, calculando su próxima corrida. Equivale a "crear el pipeline" pero sin la UI — útil para cargar pipelines de forma programática o versionados en archivos.

3. Sembrar datos de demo (agregado en Fase 4A, para probar sin SQL Server):

dotnet run --project DataPipeline.Cli -- seed-demo <metadata.db> <data.db>

Registra un pipeline demo y siembra 5 filas de ejemplo en el serving (ya con columnas de control). Sirve para probar el flujo PULL (GET/ack) sin tener un SQL Server con datos.

5 La API — endpoints

Base: https://localhost:7221 (y http://localhost:5127). Basic Auth con dos credenciales:

  • pull / pull123 — rol PULL: solo lectura de datos servidos.
  • admin / admin123 — rol ADMIN: gestión (pipelines, datasources).

Ambas son defaults de DEV; cambiarlas en producción (ver sección 8).

MétodoRutaRolQué hace
GET/api/data/{nombre}pullFilas del serving. Por defecto solo no procesadas (?incluirProcesados=true para todas).
POST/api/data/{nombre}/procesarpullAck: marca filas como procesadas. Body { "keys": [...] }.
GET/api/pipelines · /{id}adminLista / ve un pipeline.
POST/api/pipelinesadminCrea o edita (upsert) un pipeline.
DELETE/api/pipelines/{id}adminBorra un pipeline.
GET/api/datasources · /{id}adminLista / ve un datasource (sin secretos).
POST/api/datasourcesadminCrea/edita (cifra secretos; vacío = conservar).
DELETE/api/datasources/{id}adminBorra un datasource.
POST/api/datasources/{id}/probaradminPrueba la conexión (fallo amable).
POST/api/run/{id}authCorre un pipeline on-demand.

El Admin tiene dos capas de auth: (1) login local del panel (AdminAuthService), y (2) llama a la Api con la credencial admin (config ApiAuth del Admin).

7 Cómo ejecutar todo

Requisitos: .NET 10 SDK. Desde la raíz D:\Sistemas\MiddleWare.

# Compilar y testear toda la solución
dotnet build
dotnet test

# Correr la API (deployable). Crea metadata.db y data.db en su carpeta.
dotnet run --project DataPipeline.Api          # https://localhost:7221

# Correr el Admin (UI). Necesita la API arriba y la clave Syncfusion (sección 8).
dotnet run --project DataPipeline.Admin

# Usar el CLI (sección 4)
dotnet run --project DataPipeline.Cli -- seed-demo DataPipeline.Api/metadata.db DataPipeline.Api/data.db
dotnet run --project DataPipeline.Cli -- import mi-pipeline.json DataPipeline.Api/metadata.db
dotnet run --project DataPipeline.Cli -- mi-pipeline.json salida.db

8 Configuración

API — DataPipeline.Api/appsettings.json

  • ConnectionStrings:Metadata — BD de definiciones/historial/datasources (default metadata.db).
  • ConnectionStrings:Data — BD de serving (default data.db). Acá aterrizan los datos.
  • Encryption:Key — clave AES base64 (32 bytes) para cifrar secretos. Cambiar en producción (el default son 32 ceros).
  • PullAuth / AdminAuth — usuario + PasswordHash (BCrypt). Hoy pull123 / admin123 (DEV).

Admin — DataPipeline.Admin/appsettings.json

  • SyncfusionLicenseKey — clave de licencia Syncfusion. No commitear (local / user-secrets / variable de entorno).
  • ApiBaseUrl — URL de la API (https://localhost:7221).
  • ApiAuth:Username/Password — credencial con la que el Admin llama a la API (admin/admin123).
  • ApiAcceptAnyServerCertificate — true para aceptar el cert dev self-signed (solo dev).

Secreto de runtime: DataPipeline.Admin/admin-credentials.json (password local del panel hasheada) está gitignoreado — no se commitea.

9 Probar el flujo PULL sin SQL Server (demo)

# 1) (arranque limpio) borrar DBs viejas para evitar drift de esquema
rm -f DataPipeline.Api/metadata.db DataPipeline.Api/data.db

# 2) sembrar el pipeline 'demo' + 5 filas en el serving
dotnet run --project DataPipeline.Cli -- seed-demo DataPipeline.Api/metadata.db DataPipeline.Api/data.db

# 3) arrancar la API
dotnet run --project DataPipeline.Api

# 4) ejercer el ciclo (otra terminal)
curl -k -u pull:pull123 "https://localhost:7221/api/data/demo"                 # 5 filas no procesadas
curl -k -u pull:pull123 -X POST "https://localhost:7221/api/data/demo/procesar" \
     -H "Content-Type: application/json" -d "{\"keys\":[\"1\",\"2\"]}"          # ack de 1 y 2
curl -k -u pull:pull123 "https://localhost:7221/api/data/demo"                 # quedan 3,4,5
curl -k -u pull:pull123 "https://localhost:7221/api/data/demo?incluirProcesados=true"  # las 5

_key = el valor de la columna clave (en la demo, id), por eso se ackea con "1", "2".

10 Convenciones y workflow del repo

  • Idioma: enums/propiedades de dominio en castellano; interfaces/tipos de runtime/servicios/métodos en inglés (.NET); variables locales y comentarios en español. Sin tildes ni ñ en identificadores.
  • Streaming obligatorio: los transforms procesan lote a lote, nunca materializan todo.
  • Core sin dependencias externas (solo BCL).
  • Build pristine (0 warnings) — verificar con dotnet build --no-incremental.
  • TDD donde es testeable (motor, persistencia, API). La UI del Admin se verifica con build + prueba manual.
  • Git: commit directo a main, uno por tarea (sin remoto). No usar git add -A; stagear rutas explícitas.
  • Plan-driven: cada fase/rebanada pasa por brainstorming → spec → plan → ejecución (en docs/superpowers/); ledgers de avance en .superpowers/sdd/.

11 Estado y qué falta

Completo Fase 1 (cimientos), Fase 2 (motor usable + PULL), Fase 3 (UI Admin: 3A–3E), Fase 4A (serving con ciclo de procesado). Build pristine, 58 tests verdes.

Pendiente (Fase 4): reintentos (Polly), watermark del origen, dead-letter, encadenamiento (RunAfter), 2do source heterogéneo (MySQL/Oracle/Excel/RestApi), y SqlServerDataStore configurable (diferido). Decisiones de diseño en docs/superpowers/fase4-roadmap-decisiones.md. Orden sugerido: 4C → 4B → 4E → 4F → 4G.

Limitaciones actuales a tener presentes

  • El único origen que ejecuta es SQL Server (los demás tipos son Fase 4G).
  • El destino es siempre la SQLite de serving (intermedia); el destino final lo hace el consumidor.
  • ModoEscritura.Combinar no se ofrece (el store lo rechaza); el upsert se logra con Reemplazar.
  • El editor no expone RunAfter todavía (su ejecución es Fase 4F).
